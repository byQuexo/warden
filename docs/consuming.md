# Using warden

Three ways in, same engine.

## 1. Gateway (any language, no code)

Put the gateway between your agents and your MCP servers.

```bash
warden catalog pull --gateway gateway.yaml --dev   # discover tools, write catalog.lock + skeleton
# classify tools in catalog.yaml (scopes, sensitivity, tags), write policy.yaml
warden lint && warden eval --suite scenarios.yaml --generate --gate
warden-gateway --config gateway.yaml
```

Agents connect to `http://gateway:8088/mcp` with the user's access token (OAuth 2.0 bearer).
Unauthenticated clients get `401` with RFC 9728 `resource_metadata`, so MCP clients can
discover the authorization server.

### gateway.yaml

```yaml
listen: 0.0.0.0:8088
public_url: https://gateway.example.com/mcp
identity: identity.yaml
policy: { catalog: catalog.yaml, policy: policy.yaml, lock: catalog.lock }
upstreams:
  github:                                  # Streamable HTTP server
    url: https://mcp.github.internal/mcp
    auth: { strategy: token-exchange, token_url: https://sts.example.com/token, client_id: gateway, secret_env: GW_SECRET, audience: github-mcp }
  files:                                   # local server, started by the gateway, spoken to over stdio
    command: [npx, -y, "@modelcontextprotocol/server-filesystem", /workspace]
    pass_env: [HOME]                       # nothing else from the gateway's environment is inherited
    resources: ["file://"]
health: { open_after_failures: 3, cooldown_ms: 30000 }   # per-upstream circuit breaker
audit:
  hmac_key_env: AUDIT_HMAC_KEY
  sinks:
    - { type: jsonl, dir: /var/log/warden, chain: gw-1, checkpoint_key_env: AUDIT_SIGNING_KEY }
    - { type: otlp, endpoint: https://otel.example.com/v1/logs, headers_env: { x-api-key: OTEL_KEY } }
kill_switch: { file: /run/warden/kill }
```

An upstream that fails `open_after_failures` times in a row is taken out of `tools/list`
(clients get `list_changed`) and calls to it fail fast until the cooldown has passed; the
next success brings it back. Transitions are audited (`upstream_down` / `upstream_up`) and
shown in `GET /v1/upstreams`. The `otlp` sink sends every audit event as an OpenTelemetry log
record (OTLP/HTTP JSON, batched, best effort); keep a `jsonl` sink as the system of record.

Editors validate and complete all config files: JSON Schemas are in
[`spec/schema/`](../spec/schema) (generated by `warden schema --out spec/schema`, checked in CI),
and every example starts with a `# yaml-language-server: $schema=…` line.

### Token service

`warden sts --config sts.yaml` adds what most IdPs cannot issue: delegation chains.

```yaml
issuer: https://sts.example.com
key_file: sts-key.pem                       # warden dev keygen > sts-key.pem
trust: idp.yaml                             # identity.yaml of the IdP whose tokens may be exchanged
policy: policy.yaml                         # may_delegate_to edges are enforced on exchange
listen: 0.0.0.0:9400
clients:
  acme-bot: { secret_env: BOT_SECRET }
  console:  { secret_env: CONSOLE_SECRET, can_revoke_subjects: true }
```

Endpoints: `/.well-known/openid-configuration`, `/jwks`, `/token` (client credentials and
RFC 8693 token exchange with `delegate_to`), `/introspect` (RFC 7662) and `/revoke` (RFC 7009,
or `sub=<user>` to revoke every token of a user). Without `--dev` it refuses plain-HTTP
issuers, literal secrets and a missing signing key. To make revocation take effect at the
gateway immediately, add `introspection:` to the issuer in the gateway's `identity.yaml`
(see the [policy reference](policy-reference.md#identityyaml)).

### CI gate for your own policy

```yaml
# .github/workflows/policy.yml
on: [push, pull_request]
jobs:
  warden:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: byQuexo/warden@main
        with:
          working-directory: agents/policy
          suites: eval/reference.yaml
          lock: catalog.lock
```

The action lints strictly, runs your scenarios plus generated attacks and mutation testing,
writes the report to the job summary and fails the job on any gate.

### Admin API

Operators use the admin API (separate port, bearer token):

| Endpoint | Purpose |
|---|---|
| `POST /v1/explain` `{principal, action, context?}` | full decision trace |
| `POST /v1/effective` `{principal}` | effective scopes and visible actions |
| `GET/POST /v1/kill` `{mode: off\|writes\|all}` | kill switch |
| `GET /v1/upstreams` | upstreams and their health (`state`, `consecutive_failures`) |
| `GET /v1/policy`, `GET /v1/audit/tail?n=50` | status |

### Approval webhook protocol (v1)

`POST <url>` with `X-Agent-Scope-Signature: sha256=<hex hmac of body>` (if a secret is set):

```json
{"v":1,"id":"…","subject":"sven","agent":"acme-bot","act":[],"kind":"tool","name":"crm.update_deal",
 "args":{"tenant":"dach","deal_id":"d-1","amount":80000},"args_hash":"hmac-sha256:…",
 "rule":"big-deals-need-approval","reason":"…","policy_version":"sha256:…"}
```

Answer `{"decision": "approve" | "deny", "approver": "lead@acme", "reason": "…"}`. Optionally echo
`args_hash`; a mismatch fails the approval. The gateway rejects self-approval, re-checks the
policy and forwards exactly the approved arguments. Clients that send a `progressToken` and
accept SSE receive `notifications/progress` while waiting.

## 2. Rust, in-process

```rust
use warden_core::{Action, Context, Effect, Engine};
use warden_identity::Verifier;

let engine = Engine::builder()
    .policy_yaml(include_str!("policy.yaml"))
    .catalog_yaml(include_str!("catalog.yaml"))
    .build()?;                                     // lint errors = Err, never half-loaded

let verifier = Verifier::new(identity_config);
let principal = verifier.verify(bearer, warden_identity::now_unix()).await?;

let d = engine.check(&principal, &Action::tool("crm.update_deal", args), &Context::default());
match d.effect {
    Effect::Allow => run().await,
    Effect::RequireApproval => ask_a_human(&d).await,
    Effect::Deny => return Err(d.model_message),   // never show d.reason to the model
}
```

Use `engine.filter(&principal, &ActionKind::Tool, names, &ctx)` to decide what to put into the
model's tool list, and `engine.explain(…)` / `Decision::render()` for debugging.

## 3. TypeScript (WebAssembly)

```ts
import { createScope, guard, verifyToken } from "warden";
import { withScope } from "warden/mcp";
import { scopeTools } from "warden/ai-sdk";

const scope = createScope({ policyYaml, catalogYaml });
const principal = await verifyToken(bearer, { identityYaml });

// any function
const updateDeal = guard(scope, () => principal, "crm.update_deal", rawUpdateDeal, { approver });

// your own MCP server (@modelcontextprotocol/sdk)
const scoped = withScope({ listTools, callTool }, scope, { principal: (extra) => verifier.verify(extra.authInfo.token), prefix: "crm." });

// Vercel AI SDK tool map
const tools = scopeTools(scope, principal, { list_deals, update_deal }, { prefix: "crm." });
```

Build the package from source:

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.130
cd packages/warden && npm install && npm run build:wasm && npm test
```

## Extending

* **Your IdP**: write a `mapping:` (JSON pointers) or add a preset YAML under
  `crates/warden-core/presets/` plus token vectors in `spec/vectors/tokens.yaml`.
* **Attributes from a directory**: implement `warden_identity::AttributeResolver`
  (async) or use the HTTP resolver (`attributes: { resolver: http, url: …/{subject.id} }`).
* **Audit destination**: implement `warden_audit::AuditSink`; return an error to make the
  gateway fail closed.
* **Approvals**: implement `warden_gateway::Approver` or speak the webhook protocol.
* **Custom argument checks**: `Engine::builder().custom("name", Arc::new(|v, p, ctx| Tri::True))`
  and `require: { arg: x, custom: name }` (Rust only; lint warns that the policy is not portable).
